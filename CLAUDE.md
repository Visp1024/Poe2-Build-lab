## Verifying UI changes

**Auto-rule**: whenever you edit anything that touches the rendered UI —
- any file under `PBLApp/Views/**` (XAML or code-behind),
- any `*ViewModel.cs` under `PBLApp.Core/`,
- styles, converters, or assets that flow into the visual layer —

**always finish by running `/pbl-verify`** before claiming the task done.
`/pbl-verify` rebuilds, launches the client with IPC enabled, opens the test
build, captures a screenshot via the `pbl-engine` MCP server, and reads the PNG
back into the conversation so both you and the user can sanity-check the
result. A green build is not enough; you must see the screenshot.

If `pbl-engine` MCP tools aren't connected, ask the user for `/mcp`
reconnect; do not assume the client is in the state you left it.

Use `/pbl-check` (no rebuild) for quick re-snaps when the client is already
running and you want to inspect a different tab / slot.

## What This Project Is

Path of Building is a Lua-based desktop application (using a custom SimpleGraphic C++/DirectX renderer) that serves as a build planner for Path of Exile 2. The entire application logic is in Lua 5.1/LuaJIT.

## Running the Application

Run the program from the repo root — this auto-enables Dev Mode:
```
./runtime/Path of Building-PoE2.exe
```

Dev Mode features:
- `F5` — restart in-place
- `Ctrl+~` — toggle console
- `Ctrl+F5` — rebuild `src/Data/ModCache.lua` (required after mod parsing changes)
- `ConPrintf()` — print to console
- Hold `Alt` — show internal modifiers on tooltips and unrecognised nodes on the tree

## Running Tests

Tests use the [Busted](https://lunarmodules.github.io/busted/) framework. The recommended way is via Docker:
```
docker-compose up
```

To run locally (requires LuaJIT and busted installed):
```
busted --lua=luajit
```

Tests live in `spec/System/`. The `.busted` config sets the working directory to `src/`, uses `HeadlessWrapper.lua` as the test helper, and excludes tags `builds` by default.

To run a single spec file:
```
busted --lua=luajit spec/System/TestSkills_spec.lua
```

## Key Commands

- **Regenerate ModCache** (after editing mod parsing): `Ctrl+F5` in the running app, or hold `Ctrl` while launching. Always commit the resulting `src/Data/ModCache.lua`.
- **Update manifest**: `python update_manifest.py` (requires Python 3.10+)
- **Export game data from GGPK**: Use `src/Export/Launch.lua` via the runtime executable (see CONTRIBUTING.md for full setup).

## Architecture

### Entry Points and Loading

`src/Launch.lua` is the program entry point. It initializes the renderer, detects dev mode, and loads `Modules/Main`. `HeadlessWrapper.lua` provides a headless stub environment for tests.

### Directory Layout

- **`src/Modules/`** — Core logic. No UI rendering; all calculation, data loading, and build orchestration.
- **`src/Classes/`** — UI components. Each file is a control or tab (e.g., `CalcsTab.lua`, `ItemsTab.lua`, `TreeTab.lua`).
- **`src/Data/`** — Auto-generated data files. Files with the header `-- This file is automatically generated, do not edit!` must be regenerated via `src/Export/` scripts, not edited manually.
- **`src/Export/`** — Scripts for extracting data from the PoE2 GGPK game files.
- **`src/TreeData/`** — Passive skill tree versions (versioned zip files extracted here).
- **`spec/System/`** — Busted test specs.

### Calculation Pipeline

The calculation flow is:
1. **`CalcSetup.lua`** — Builds mod databases for player and enemy actors; applies all items, skills, passives, flasks, jewels, bandits, pantheon.
2. **`CalcOffence.lua`** (339 KB) / **`CalcDefence.lua`** (237 KB) — Compute all offensive and defensive stats.
3. **`CalcSections.lua`** — Organises results for display in sidebar and Calcs tab.
4. **`Calcs.lua`** — Orchestrates the above; exposes `buildOutput` used by UI.

`CalcActiveSkill.lua`, `CalcPerform.lua`, `CalcTriggers.lua`, `CalcMirages.lua`, and `CalcBreakdown.lua` handle specific sub-domains.

### Mod System

- **`Modules/ModParser.lua`** (655 KB) — Parses raw game mod strings using Lua patterns.
- **`src/Data/ModCache.lua`** (985 KB) — Pre-compiled output of `ModParser`; loaded at startup for fast lookups. Regenerated with `Ctrl+F5`.
- **`Modules/ModTools.lua`** — Creates mod objects and loads the `ModCache`.
- **`Classes/ModDB.lua`**, **`ModList.lua`**, **`ModStore.lua`** — Runtime mod storage and querying.

When changing mod parsing, always regenerate and commit `ModCache.lua`.

### Build Orchestration

**`Modules/Build.lua`** is the central orchestrator. It loads a build XML, initialises all tab components (`TreeTab`, `SkillsTab`, `ItemsTab`, `ConfigTab`, `CalcsTab`), drives recalculation, manages undo/redo, and handles import/export (PoE.com profile imports, share codes).

### UI Framework

All UI controls extend `Classes/Control.lua`. The tab system (`TreeTab`, `ItemsTab`, `SkillsTab`, `ConfigTab`, `CalcsTab`, `NotesTab`) lives in `Classes/`. Tooltips use `Classes/Tooltip.lua` and `Classes/TooltipHost.lua`.

### Data Files

`src/Data/Global.lua` defines colour codes, mod flags, keyword enums, and skill type definitions — the central enum/constant registry. `src/Data/Gems.lua` (490 KB) contains all gem/skill data.

## PR Guidelines

- All PRs must target the `dev` branch.
- If mod parsing changes, include the regenerated `src/Data/ModCache.lua`.
- If `src/Export/` scripts change, include all regenerated `src/Data/` files.
- Backward compatibility is required for mod text (old builds store raw mod strings).

## C# Projects (PBLHost directory)

A parallel C# solution lives in `PBLHost/` and hosts the PoB Lua engine via NLua (.NET 9, Lua 5.4). These projects are separate from the Lua application above.

### Solution Layout

```
PBLHost/          PBLHost.sln entry point (console verification runner)
PBLEngine/        Shared class library — NLua host, BuildModel
PBLApp.Core/      MVVM ViewModels — no Avalonia dependency
PBLApp/           Avalonia 12 UI (XAML views, ViewLocator)
PBLMcp/           MCP stdio server for agent testing
```

### Build & Run

```powershell
# From repo root
cd PBLHost
dotnet build PBLHost.sln          # build all projects
dotnet run --project PBLHost      # run verification (10 tests)
dotnet run --project PBLMcp       # start MCP server (stdio)
dotnet run --project PBLApp       # launch Avalonia GUI
```

### PBLEngine

`PBLEngine/LuaHost.cs` — wraps NLua 1.7.3 (Lua 5.4 via KeraLua).
- `Initialize(repoRoot)` — sets CWD to `src/`, loads `lua/compat.lua`, then `HeadlessWrapper.lua`
- `NewBuild()`, `LoadBuildFromXml(xml, name)`, `SaveBuildToXml()`, `GetStat(name)`, `GetAllStats()`

`PBLEngine/BuildModel.cs` — typed stat properties (`TotalDps`, `Life`, `Mana`, `EnergyShield`, etc.) plus `AllStats: IReadOnlyDictionary<string,object?>`. Implements `INotifyPropertyChanged`.

`PBLEngine/lua/compat.lua` — LuaJIT 5.1 → Lua 5.4 shims: `unpack`, `arg`, `loadstring`, `math.atan2`, `math.log10`, `string.format` float→int fix, full `bit` library, `jit` stub, `lua-utf8` stub, `io.read` stub.

**Critical Lua 5.4 differences vs LuaJIT:**
- `integer / integer = float` (e.g. `25/1 = 25.0`)
- `tostring(25.0) = "25.0"` (not `"25"`)
- These broke ModParser pattern matching and CalcOffence buffer indexing — both fixed in `src/Modules/ItemTools.lua` and `src/Modules/CalcOffence.lua`.

### PBLApp.Core (ViewModels)

No Avalonia dependency — can be instantiated headlessly in tests or MCP server.

- `MainWindowViewModel` — `CurrentPage: ViewModelBase`, navigates between list and build pages. Constructor overload accepts `Task<LuaHost>` for injection.
- `BuildListViewModel` — reads `%LOCALAPPDATA%\PathOfBuilding\Builds`, `[RelayCommand] OpenBuild()`, `DeleteBuild()`, `Refresh()`.
- `BuildPageViewModel` — `IsLoading`, `LoadError`, `Build: BuildModel?`. Loads asynchronously via fire-and-forget `LoadAsync`.
- `BuildEntryViewModel` — tree node (file or folder), `Children` for nested folders.

### PBLApp (Avalonia UI)

Avalonia 12 conventions used:
- `ContentControl Content="{Binding CurrentPage}"` — ViewLocator maps `*ViewModel` → `*View`
- `TreeDataTemplate` (NOT `HierarchicalDataTemplate` — renamed in Avalonia 12)
- Double-tap on tree row triggers `OpenBuildCommand`

### PBLMcp (MCP Server)

Stdio MCP server using `ModelContextProtocol` 1.3.0. All .NET console logging suppressed (`LogLevel.None`) to keep stdout clean for JSON-RPC.

**DI setup:** `PBLState` (singleton, eager LuaHost init via `Task.Run`) → `AppDriver` (holds `MainWindowViewModel`) → tool classes via constructor injection.

**Lua stdout redirect:** Must redirect `print`/`io.write` to stderr **before** `host.Initialize()` to prevent Lua startup output from corrupting the MCP JSON-RPC stream:
```csharp
host.State.DoString(@"
    local _stderr = io.stderr
    print = function(...) ... _stderr:write(...) end
    io.write = function(...) _stderr:write(...) end
");
host.Initialize(FindRepoRoot());
```

**Tool classes:**
- `PBLTools(PBLState state)` — 9 low-level Lua tools: `new_build`, `load_build`, `get_build_xml`, `get_stats`, `set_custom_mods`, `add_skill`, `equip_item`, `list_builds`, `run_lua`
- `AppTools(AppDriver driver)` — 10 MVVM-level tools: `app_wait_for_ready`, `app_get_current_page`, `app_reset`, `app_list_builds`, `app_select_build`, `app_open_build`, `app_wait_for_build_load`, `app_go_back`, `app_assert_stat`, `build_app`

**MCP registration** (Claude Code): registered via `claude mcp add` from repo root. Config in `.claude/settings.local.json`.

**Startup latency:** LuaHost init takes ~35-45s on first call. `app_wait_for_ready` must be called first; init runs eagerly in background from process start.
